# OSATURA — Feuille de route d'implémentation ordonnée (salle blanche, sans risque de propriété intellectuelle)

Statut de ce fichier : document de planification dérivé de `FEATURES.md` (tours 1 à 9 de recherche sur sources publiques, 19 oct. 2026).
Tout ce qui suit va du **simple au complexe**, dans un ordre tel que chaque élément ne dépend que des éléments qui le précèdent.
**Ceci n'est pas un avis juridique.** Les notes de propriété intellectuelle sont un tri des risques d'ingénierie ; faites confirmer par un juriste tout ce qui est marqué 🟡 avant livraison.

Légende — Risque : 🟢 sûr (standard ouvert, mathématiques de manuel ou conception propre) · 🟡 à réexaminer avant livraison · 🔴 à ne pas faire.
Effort : S ≤ 1 jour · M = quelques jours · L = quelques semaines · XL = quelques mois.

## 0. Règles de salle blanche (valables pour chaque élément)

1. **Spécifier uniquement à partir du comportement public.** Entrées autorisées : manuels d'utilisation publiés, notes de version, vidéos des éditeurs, standards ouverts, articles universitaires, code open source sous licences compatibles (à lire pour les idées, jamais pour copier du code ; vérifiez la licence avant même de lire du code GPL que vous pourriez réimplémenter).
2. **Processus à deux rôles.** Celui qui rédige une note de fonctionnalité (`docs/specs/R-xxx.md`) cite sa source publique. Celui qui l'implémente ne lit que cette note + les standards/articles, pas les rouages internes du produit de l'éditeur.
3. **Journal de provenance.** Chaque élément reçoit une ligne dans `CLEANROOM.md` : id de l'élément · sources publiques · date · implémenteur. (R-001)
4. **Ne jamais** utiliser de versions crackées/piratées, de documents ayant fuité, de décompilation, ni de rétro-ingénierie du trafic réseau des concurrents. (Dans l'UE, la directive 2009/24/CE limite la décompilation à des cas étroits d'interopérabilité — nous ne nous y appuyons pas.)
5. **Noms propres, formats propres.** Utilisez notre vocabulaire (pilote de pose, et non « Smart Bone » ; take/clip, et non « replay »). Les noms des concurrents n'apparaissent qu'à titre descriptif dans la documentation (usage nominatif), jamais dans l'interface, les extensions de fichier, les crates ou le marketing.
6. **Formats ouverts uniquement pour l'échange** (liste au §2). Les formats binaires propriétaires sont exclus, sauf si l'éditeur publie une licence qui l'autorise.
7. **Brevets :** privilégiez les algorithmes de manuel ou plus anciens, et nos propres conceptions. Évitez de réimplémenter toute technique faisant l'objet d'une revendication de brevet connue (voir §3).
8. **Codecs :** gardez les encodeurs externes (ffmpeg installé par l'utilisateur). Utilisez par défaut des codecs à spécification ouverte (VP9/AV1/APNG/PNG) ; leur statut au regard des brevets n'est pas évalué (docs/PATENT_NOTES.md). Considérez H.264/AAC/ProRes comme optionnels, côté utilisateur, avec une note.
9. **Polices, pinceaux, illustrations d'exemple :** uniquement CC0/OFL/œuvre propre.

## 4. Innovations — idées introuvables dans toutes les sources consultées (tours 1 à 9)

« Introuvable » signifie : je ne les ai vues ni dans les pages des éditeurs, ni dans les notes de version, forums, dépôts, avis ou articles que j'ai lus. Elles peuvent exister ailleurs ; considérez la nouveauté comme non vérifiée tant qu'une recherche d'antériorité n'a pas été faite. Chacune s'appuie sur ce que possède déjà OSATURA : **evaluate(frame) est une fonction pure**, **chaque édition est une opération JSON-pointer avec un inverse exact**, **chaque édition est revalidée**, **tout est déterministe**.

## 8. De meilleures alternatives en salle blanche pour chaque élément 🟡 / 🔴 (implémentées)

Principe : remplacer chaque élément risqué par quelque chose qui est **(a) fondé sur un standard ouvert public ou des mathématiques de manuel, (b) notre propre conception là où aucun standard n'existe, et (c) au moins aussi capable**. Le statut ci-dessous correspond à du code réel avec des tests (185 réussis).

Les pins sont animables (`PinDx/PinDy`). |
